# 通用程式碼審查檢查清單

本檢查清單適用於所有技術棧，涵蓋通用的程式碼品質、安全性和最佳實踐。

## 1. 安全性

### 輸入驗證
- [ ] 所有使用者輸入是否經過驗證和清理？
- [ ] 是否防範 SQL Injection（使用參數化查詢/ORM）？
- [ ] 是否防範 XSS 攻擊（適當的輸出編碼）？
- [ ] 是否防範 CSRF 攻擊（CSRF token）？
- [ ] 檔案上傳是否有類型和大小限制？

### 認證與授權
- [ ] 密碼是否使用強雜湊演算法（bcrypt、Argon2）？
- [ ] 敏感資料是否加密儲存？
- [ ] Token/Session 是否安全儲存？
- [ ] 是否實作適當的授權檢查？
- [ ] 是否避免硬編碼的認證資訊？

### 資料保護
- [ ] 敏感資料是否避免記錄在日誌中？
- [ ] API 回應是否避免洩漏內部資訊？
- [ ] 是否使用 HTTPS 傳輸敏感資料？
- [ ] 是否適當處理個人資料（GDPR 合規）？

### 依賴安全
- [ ] 第三方套件是否為最新穩定版本？
- [ ] 是否檢查已知的安全漏洞（npm audit、OWASP）？
- [ ] 是否避免使用已廢棄的套件？

## 2. 程式碼品質

### 命名與可讀性
- [ ] 變數、函數、類別名稱是否清晰且有意義？
- [ ] 是否遵循專案的命名慣例？
- [ ] 是否避免縮寫（除非是通用縮寫）？
- [ ] Boolean 變數是否使用 is/has/should 前綴？

### 函數與方法
- [ ] 每個函數是否只做一件事（單一職責原則）？
- [ ] 函數長度是否合理（建議 <50 行）？
- [ ] 參數數量是否合理（建議 ≤5 個）？
- [ ] 是否避免巢狀層級過深（建議 ≤3 層）？
- [ ] 複雜邏輯是否提取為獨立函數？

### 重複程式碼
- [ ] 是否避免複製貼上程式碼？
- [ ] 重複邏輯是否提取為共用函數？
- [ ] 是否適當使用繼承/組合/介面？

### 錯誤處理
- [ ] 是否適當處理所有可能的錯誤情況？
- [ ] 錯誤訊息是否清晰且對使用者友善？
- [ ] 是否記錄錯誤日誌（但不洩漏敏感資訊）？
- [ ] 是否避免空的 catch 區塊？
- [ ] 資源是否在 finally/defer 中正確釋放？

### 跨服務契約（enum / DTO）

適用於**前後端分離**或**多 repo**專案。diff 若動到「會從 API 回應解析的 enum 或 DTO 欄位」時檢查：

- [ ] enum 的常數值是否與**後端原始碼**逐字一致？（❌ 不可只看 API 文件——文件常落後或誤植）
- [ ] 解析方式是 **fail-hard 還是 fail-soft**？
      fail-hard（如 Dart `json_serializable` 的 `$enumDecode`、非 nullable 欄位）遇到未知值會**拋錯**，
      而 `fromJson` 通常是整批解析 → **一筆未知值會讓整個列表解析失敗、整頁空白**，
      不是單列顯示異常
- [ ] 若為 fail-hard，是否有**契約測試**鎖住值清單？（後端新增值時能在測試層先發現）
- [ ] 是否考慮 fail-soft fallback（如 `unknownEnumValue`）？若採用，未知值是否會記 log
      而非靜默忽略？（靜默 fallback 會把問題藏起來）
- [ ] 該 enum 的 `values` 是否被當作 UI 選項來源（下拉／篩選）？
      若是，新增 fallback 值（如 `UNKNOWN`）會出現在使用者可見選單中，需額外過濾

> ⚠️ **review 的能力邊界**：此清單只能攔住「**本次 diff 新增或修改**」的 enum。
> 最常見的失效模式是「**後端新增值、前端零改動**」——那種情況前端沒有任何 diff，
> **code review 不可能發現**，只能靠契約測試或 fail-soft 解析。
> 因此發現 fail-hard 解析時，應直接建議加契約測試，而不是只確認「這次改對了」。

### 註解與文件
- [ ] 複雜邏輯是否有註解說明？
- [ ] 公開 API 是否有文件註解？
- [ ] 是否避免無意義的註解（如 `// 設定變數`）？
- [ ] TODO/FIXME 是否標記暫時性解決方案？
- [ ] 是否移除註解掉的程式碼（使用版本控制）？

## 3. 效能

### 資料庫與 API
- [ ] 是否避免 N+1 查詢問題？
- [ ] 資料庫查詢是否有適當的索引？
- [ ] 是否避免在迴圈中進行 API 呼叫？
- [ ] 大量資料是否分頁處理？
- [ ] 是否使用快取減少重複查詢？

### 演算法與資料結構
- [ ] 演算法複雜度是否合理？
- [ ] 是否選擇適當的資料結構（Map vs List）？
- [ ] 是否避免不必要的迴圈和計算？
- [ ] 大型集合操作是否優化（stream、lazy evaluation）？

### 記憶體管理
- [ ] 是否避免記憶體洩漏（未釋放的資源）？
- [ ] 大型物件是否適時釋放？
- [ ] 是否避免不必要的物件創建？
- [ ] 迴圈內是否避免創建臨時物件？

### 非同步與併發
- [ ] 長時間運行的任務是否非同步執行？
- [ ] 是否避免阻塞主執行緒/UI 執行緒？
- [ ] 併發操作是否有適當的同步機制？
- [ ] 是否避免 Race Condition？
- [ ] Async 操作是否有錯誤處理和取消機制？

## 4. 可維護性

### 程式碼組織
- [ ] 檔案和目錄結構是否清晰？
- [ ] 相關功能是否放在同一模組？
- [ ] 是否遵循專案的架構模式？
- [ ] 是否避免循環依賴？

### 設計原則
- [ ] 是否遵循 SOLID 原則？
  - Single Responsibility（單一職責）
  - Open/Closed（開放封閉）
  - Liskov Substitution（里氏替換）
  - Interface Segregation（介面隔離）
  - Dependency Inversion（依賴反轉）
- [ ] 是否適當使用設計模式？
- [ ] 是否避免過度設計？

### 測試
- [ ] 關鍵邏輯是否有單元測試？
- [ ] 測試覆蓋率是否足夠？
- [ ] 是否有整合測試驗證主要流程？
- [ ] Edge case 是否有測試覆蓋？
- [ ] 測試是否獨立且可重複執行？

### 配置管理
- [ ] 配置是否從程式碼中分離？
- [ ] 環境特定配置是否正確處理（dev/staging/prod）？
- [ ] 敏感配置是否使用環境變數或密鑰管理系統？
- [ ] 是否避免在程式碼中硬編碼配置值？

## 5. 程式碼風格

### 格式化
- [ ] 是否使用一致的縮排（spaces/tabs）？
- [ ] 行長度是否符合專案規範（建議 80-120 字元）？
- [ ] 是否使用自動格式化工具（Prettier、Black、gofmt）？
- [ ] 空白行是否適當使用增加可讀性？

### 語言特定慣例
- [ ] 是否遵循語言的官方風格指南？
  - Python: PEP 8
  - Java: Oracle Code Conventions
  - JavaScript: Airbnb/Standard
  - Go: Effective Go
  - Kotlin: Kotlin Coding Conventions
- [ ] 是否使用 Linter 檢查程式碼風格？
- [ ] 是否通過專案的 CI 檢查？

### Magic Number 和常數
- [ ] 是否避免 Magic Number？
- [ ] 常數是否定義為具名常數？
- [ ] 常數是否放在適當的位置（檔案頂部、配置檔）？

## 6. API 設計（如適用）

### RESTful API
- [ ] HTTP 方法使用是否正確（GET/POST/PUT/DELETE）？
- [ ] URL 設計是否符合 REST 原則？
- [ ] HTTP 狀態碼是否正確？
- [ ] API 版本控制是否適當？
- [ ] 是否有適當的限流（Rate Limiting）？

### 回應格式
- [ ] 回應格式是否一致？
- [ ] 錯誤回應是否包含有用的資訊？
- [ ] 是否使用適當的 Content-Type？
- [ ] 分頁回應是否包含必要的元數據？

### 文件
- [ ] API 是否有清楚的文件（Swagger/OpenAPI）？
- [ ] 參數和回應格式是否有文件說明？
- [ ] 是否有使用範例？

## 7. 版本控制

### Commit
- [ ] Commit 訊息是否清楚描述變更？
- [ ] 是否遵循專案的 commit 訊息規範？
- [ ] 每個 commit 是否是一個邏輯完整的變更？
- [ ] 是否避免包含無關的變更？

### 分支管理
- [ ] 是否在正確的分支上開發？
- [ ] 是否與主分支保持同步？
- [ ] 合併衝突是否正確解決？

## 8. 變更政策

### 最小化變更
- [ ] 是否只修改必要的部分？
- [ ] 是否避免「順手重構」無關程式碼？
- [ ] 變更範圍是否可控且清晰？

### 向後相容性
- [ ] 是否保持 API 向後相容？
- [ ] 資料庫變更是否有遷移腳本？
- [ ] 是否避免破壞性變更（或有適當的版本升級）？

### 文件更新
- [ ] README 是否需要更新？
- [ ] API 文件是否需要更新？
- [ ] 變更日誌是否記錄？

## 使用建議

1. **優先級排序**：
   - 🔴 Critical: 安全性問題、破壞性變更
   - 🟡 Warning: 程式碼品質、效能問題
   - 🟢 Suggestion: 風格、可維護性建議

2. **與技術棧特定檢查清單結合**：
   - 先檢查通用項目（本檔案）
   - 再檢查技術棧特定項目（flutter-riverpod.md、springboot.md 等）

3. **持續改進**：
   - 根據實際問題更新檢查清單
   - 記錄常見問題作為未來參考

4. **自動化檢查**：
   - 使用 Linter（ESLint、Pylint、Ktlint）
   - 使用安全掃描工具（SAST、OWASP Dependency-Check）
   - 設定 CI/CD 自動檢查
