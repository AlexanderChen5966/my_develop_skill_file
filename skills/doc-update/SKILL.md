# Doc Update

Code review 通過後的文件收尾工作：將 docs/shared/ 的任務文件標記為已完成，並同步更新 CHANGELOG.md；最後判斷這次學到的東西要不要沉澱（Step 7）。

## 工作流程

### Step 1：確認本次變更範圍

```bash
# 查看本次變更的檔案
git diff HEAD~1 --name-only 2>/dev/null || git diff --cached --name-only
```

若使用者已明確指定任務名稱或文件，直接跳到 Step 3。

### Step 2：找到對應的任務文件

先確認 `docs/shared/` 目錄存在：

```bash
ls docs/shared/ 2>/dev/null
```

若目錄不存在，告知使用者「此專案沒有 docs/shared/ 目錄，無法更新任務文件」並停止。

列出狀態為「待實作」或「進行中」的文件：

```bash
grep -l -E "待實作|進行中" docs/shared/*.md
```

對照 Step 1 的變更檔案路徑，比對文件中提到的「目標檔案」或「影響範圍」，找出對應的任務文件。

若有多份候選文件，向使用者確認後再繼續。

### Step 3：讀取任務文件並確認狀態

閱讀找到的任務文件，**先確認狀態**：

- 若狀態已是 `**✅ 已完成**`：**立即停止**，告知使用者「該文件已標記為完成，無需更新」，不執行任何後續步驟。
- 若狀態為 `**⏳ 待實作**` 或 `**🔄 進行中**`：繼續執行，理解：
  - 原計劃的任務步驟
  - 執行步驟清單
  - 相關檔案清單

### Step 4：更新任務文件狀態

**4a. 更新 `## 狀態` 區塊**

不論原本是「⏳ 待實作」或「🔄 進行中」，統一改為（使用今天實際日期）：
```
## 狀態

**✅ 已完成**（YYYY-MM-DD）
```

**4b. 標記各任務標題**

在 `### 任務 N：` 標題末尾加上 ✅：
```
### 任務 1：新增常數 ✅
```

**4c. 標記執行步驟**

在「## 執行步驟」的每個步驟末尾加上 ✅：
```
步驟 1：修改 order_data_table.dart ✅
步驟 2：執行靜態分析 ✅
```

**4d. 更新驗收清單（如有）**

若文件中有手動驗證的核取方塊 `[ ]`，全部改為 `[x]`：
```
→ [ ] 短品項名稱：正常顯示  改為  → [x] 短品項名稱：正常顯示
```

**4e. 記錄實際與計劃的差異（僅當有差異時）**

若實際實作與計劃不同（例如改用不同 API、調整了邏輯），在文件底部的「## 相關檔案」之後追加：

```markdown
## 實際實作備註

- [說明差異，例如：「Tooltip 改用 waitDuration 參數避免閃爍」]
```

無差異時不需要加此區塊，保持文件簡潔。

### Step 5：更新 CHANGELOG.md

在 `## [Unreleased]` 下加入對應條目，依變更性質分類：

| 類別 | 適用情境 |
|------|---------|
| `Added` | 新功能、新欄位、新頁面 |
| `Changed` | UI 調整、行為變更 |
| `Fixed` | Bug 修正 |

格式：
```markdown
### Added
- [一行功能簡述，用繁體中文]
```

若 `[Unreleased]` 下已有相關項目，合併描述而非重複新增。

### Step 6：更新 docs/shared/readme.md 索引

更新任務文件在索引中的狀態標記，並確認分類正確。

索引格式：
```markdown
### AI Agent 任務佇列

| 文件 | 功能 | 狀態 |
|------|------|------|
| [order_fuel_type_ellipsis_tooltip.md](./order_fuel_type_ellipsis_tooltip.md) | 品項欄截斷 + Hover Tooltip | ✅ 已完成 |
| [invoice_status_update_task.md](./invoice_status_update_task.md) | 發票狀態更新 | ✅ 已完成 |
```

詳見 [references/readme-format.md](references/readme-format.md) 了解完整的 readme.md 目標格式。

### Step 7：沉澱判斷（這次學到的東西要不要留、留在哪）

任務剛收尾、細節還記得最清楚的時候，判斷一次。**大多數任務的答案是「不用留」**。

#### 7a. 門檻：三個都成立才留

1. **不明顯**：看最終的程式、測試、型別、註解、既有文件，看不出這件事
2. **長期有用**：是規則、限制、根因、被否決的做法或決定，不只是這次 diff 的經過
3. **忘了會出事**：忘記的話，很可能重犯、帶來風險，或要花大量時間重新查

反事實檢驗：**這份紀錄如果不存在，下一個人只看程式，會不會再犯同樣的錯、或重新查一遍？** 不會，就不留。

不成立 → 在回報寫「沉澱判斷：本次無需沉澱（理由一句）」，結束。

#### 7b. 選最便宜、能擋住重犯的形式（由上往下，選第一個做得到的）

| 順序 | 形式 | 什麼時候選 |
|---|---|---|
| 1 | **測試**（跟著程式走） | 錯誤能被測試抓到。例：「按 x 會清欄位並重抓」，下一個新頁面寫錯就紅燈 |
| 2 | **專案規則**：`AGENTS.md`、`.claude/rules/` | 測試抓不到，但寫成一條規則就能防。例：`list-page-header.md` 加「`onClearPressed` 要清該欄位並觸發 fetch」 |
| 3 | **三層記憶**（照全域 CLAUDE.md 的寫入規則分層） | 跟這個專案的程式無關、但換情境仍成立的經驗；跨專案寫 shared，個人原則寫 global |
| 4 | **專案文件**：project-documentation 的 Bug 修復紀錄 | 要保留根因追查過程、試過但沒用的做法、量測數據 |
| 5 | **公司共用知識**：slc-core `/knowledge-capture`（開 MR） | 跨 repo、其他同事也會踩到、已實際查證的事實 |

其他東西的歸處：只跟這次修改有關的經過 → MR 說明（`pr`）；局部的「為什麼這樣寫」→ 程式註解。

#### 7c. 先找重複

照選定的形式去找：既有測試、規則檔、記憶索引（`MEMORY.md`）、`docs/bug_record/`。**同一件事已經有了，就提議更新那一份**，不新增第二份。

#### 7d. 先給使用者看，同意後才寫

列出：門檻判斷（三條各一句）、選的形式與理由、要寫的位置、草稿全文（或測試的大綱）。**使用者同意才寫入**，和記憶的寫入規則一致。測試屬於程式碼變更，同意後照一般開發流程加，不在 doc-update 裡直接改程式。

非互動情境（`claude -p`、排程、workflow-bench）：只輸出提議，**不寫入**。

#### 7e. 和其他工具的分工

| 工具 | 管什麼 |
|---|---|
| doc-update Step 7 | 這張卡解掉的問題，學到的東西放哪 |
| `retro` | 這個 session 的工作環境（skill、規則、指令）哪裡可以改善。**只能由使用者手動叫**（`/retro`，plugin 版 `/core:retro`），本 skill 不會也叫不到它；覺得需要時在回覆裡建議使用者叫 |
| `/knowledge-capture` | 第 5 級的實際寫入流程（審查、開 MR） |

### Step 8：補流程機制的退場追蹤（試用期間）

流程 v3 的四個機制（doubt-check、source-driven、沉澱判斷、常見藉口表）都在試用，各有退場條件。每張卡結案時，在桌面〈開發流程升級_2026-11-09/v3實測報告_02-log-drawer.md〉第 8 節的四張追蹤表**各補一列**（這張卡沒用到該機制就寫「不適用」，不要跳過）：

| 機制 | 這張卡要記的 |
|---|---|
| doubt-check | 有標記的任務、有沒有照標記觸發、有沒有找到「成立且要修」的問題 |
| source-driven | 有沒有新的框架／套件用法、有沒有附出處、有沒有找到真問題（棄用 API、錯誤用法、文件矛盾靠 lock 版本解決） |
| 沉澱判斷 | Step 7 的結論（無需沉澱／提議了什麼）、使用者採不採用 |
| 常見藉口表 | 這張卡有沒有做出某張藉口表**明列**的行為（列出哪一條、哪個 skill） |

某張表滿了就照該表上方的退場條件判斷，結論交給使用者決定，不自己移除。檔案不在、或非互動情境：在回報寫「退場追蹤未補」並列出要補的內容。

## 常見藉口

| 藉口 | 為什麼不成立 |
|------|-------------|
| 「應該都做完了，直接標完成」 | 驗證清單沒做的要保留未勾、在「實際實作備註」寫明原因，不能一起打勾 |
| 「review 有小建議沒處理，不影響標完成」 | 可以標完成，但沒處理的建議要寫進備註，不能消失 |
| 「這次學到很多，全部記下來」 | 只留不明顯、長期有用、忘了會出事的；其餘交給 commit、MR 說明與程式註解 |
| 「寫成記憶最快」 | 能用測試或專案規則擋住的，就不要只寫記憶；記憶要有人想起來才有用 |
| 「沉澱很簡單，直接寫進去就好」 | 先給使用者看。寫錯的規則比沒有規則更糟 |

## 注意事項

- **日期使用今天的實際日期**，不使用文件中的「建立日期」
- **只更新狀態為「⏳ 待實作」或「🔄 進行中」的文件**，已完成的文件不再處理
- **不修改技術內容**（程式碼範例、實作說明等），只更新狀態標記與差異備註
- **若無法確認對應哪份任務文件，先問使用者**，不要猜測
