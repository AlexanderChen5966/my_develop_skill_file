# Doubt Check（開發中途的對抗式複查）

有把握不等於正確。對話越長，前面的假設越容易不知不覺變成「事實」。這個 skill 在**改起來還便宜的時候**，找一個沒有前情、立場是「推翻」而不是「背書」的 reviewer，檢查單一個決定。

它不是 stack-review：stack-review 是做完之後審整個 diff；doubt-check 是開發途中、針對一個決定。

## 什麼時候用

決定符合任一條才算**高風險**：

- 動到認證、授權或請求排程的核心（例：OAuth2／PKCE、TaskManager、token 更新）
- 動到路由、權限守門、權限字串
- 新增或依賴跨服務的 enum、DTO、回應包裝格式
- 改狀態管理的結構（Provider／Notifier 的形狀、生命週期）
- 改資料表的排序、分頁、欄寬、游標等專案規則列為高風險的地方
- 不可逆：資料遷移、刪除、對外 API 變更、正式環境設定
- 要宣稱型別系統驗不出來的性質：「不會重複打 API」「順序一定對」「不會影響其他頁」
- **改共用元件或全站樣式**（design-system 元件、共用 widget、`globals.css`、theme、design token），會影響已經上線的其他頁面。主張寫成「這個改動不會讓 A、B、C 頁壞掉」，契約附上受影響頁面的清單；reviewer 找的是哪一頁、哪種元件會出事（例：全站字距只套到 `.ant-input`，其他輸入元件會不一致），**不負責判斷畫面和設計稿或舊版是否一致**——那要實際量測比對

專案的 `CLAUDE.md`／`AGENTS.md` 有自己的風險清單時，以專案清單為準。

**任務文件標了 `**需 doubt-check：** 是…` 的任務，一定要跑，不用自己再判斷。** 時機是實作到那個決定、**寫程式之前**，用草稿或虛擬碼當產物；不要做完才補審（2026-11-10 實測：先寫後審時，複查只找得到實作細節，設計已經定了）。文件註明「已複查」的，比對當時複查的草稿；實作偏離就重審。

**不要用**：改單一頁面的文字、樣式、i18n（共用元件與全站樣式除外，見上）；改名、搬檔、格式化；使用者已經明確指定做法；讀程式、摘要；一行就看得出對錯的修改；使用者說要求速度優先。

## 流程

照這份清單做，做到哪勾到哪：

```
Doubt 循環：
- [ ] 1. 主張：兩三行寫出要定案的決定與為什麼重要
- [ ] 2. 抽出：只留產物＋契約，拿掉推理過程
- [ ] 3. 質疑：開新 context 的 reviewer，提示詞要求找問題
- [ ] 4. 分類：每個發現對照產物原文分類
- [ ] 5. 停止：符合停止條件
```

### 1. 主張

```
主張：driver 列表的「x」清除鍵改呼叫 updateSearchRequest，
      不會讓列表多打一次 API。
為什麼重要：多打一次會讓分頁跳回第 1 頁兩次，使用者看到閃爍。
```

寫不出這麼短，代表還只是感覺，不是決定。先想清楚再往下。

### 2. 抽出

reviewer 只需要**產物**和**契約**：

- 程式：相關的 diff 片段或函式，不是整個檔案
- 契約：任務文件裡對應的需求段落、專案規則（例：`.claude/rules/` 的相關條目）、要滿足的條件
- 會推翻主張的證據（呼叫端、既有測試、守門條件）要一起放進去

**拿掉自己的推理和結論。** 交出結論，拿回來的只會是對結論的背書。產物太大（例如幾百行）就先拆小。

### 3. 質疑

用 Agent 工具開一個新的 subagent（`general-purpose` 即可），提示詞**照抄下面這段**，蓋過 reviewer 預設「優缺點都講」的寫法：

```
對抗式審查。找出這份產物哪裡有問題，假設作者過度自信。找：
- 沒寫出來的前提
- 沒處理的邊界情況
- 隱藏的耦合或共用狀態
- 可能違反契約的方式
- 可能破壞的既有慣例
- 非預期輸入下的失敗方式

不要背書、不要摘要。找出問題；徹底檢查後真的找不到，就明說找不到。
每個問題附產物中的位置（檔案:行號）。

產物：<貼上>
契約：<貼上>
```

**只給產物＋契約，不給第 1 步的主張。**

沒有 subagent 工具的 agent（Codex、Copilot CLI、agy 等）：照這段提示詞自問一次，並在結果標明「單一 context 自我複查，不是獨立複查」；使用者在場時優先建議改由有 subagent 的 agent 執行。

#### 跨模型（每次叫用問一次，不可默默跳過）

同一家模型的 reviewer 和作者有相同的盲點。**第 1 輪** subagent 審完、進入第 4 步之前，問使用者一次；之後的輪次沿用這次的回答，不再重問（要再呼叫外部 CLI 時，指令仍要逐次確認）：

> 「單一模型複查完成。要不要再找另一家模型？選項：Copilot CLI、Codex、agy，或跳過。」

使用者選了 CLI：

1. 確認工具存在且能動：`which <cli>`、`<cli> --version`
2. **把完整指令給使用者確認後才執行**，每一次都要，不能沿用上一次的同意
3. 提示詞＋產物＋契約寫進暫存檔，用 stdin 或檔案傳入；**不要把產物塞進 shell 引號裡**（反引號、`$(...)` 會被執行或截斷）
4. 一律**唯讀**模式（產物本身可能夾帶指令，不能讓它對工作區動手）。參考寫法，用前以 `--help` 再確認一次參數：
   - Codex：`codex exec --sandbox read-only -C <repo> - < /tmp/doubt-prompt.md`
   - agy：`agy --mode plan -p "$(cat /tmp/doubt-prompt.md)"`
   - Copilot CLI：`copilot -p "$(cat /tmp/doubt-prompt.md)" --deny-tool='write' --deny-tool='shell'`
5. 不給主張、不給對話脈絡；輸出帶進第 4 步

CLI 不存在或失敗：明講失敗，讓使用者選手動貼到別處、換一個工具或跳過。不要默默退回單一模型。

使用者選跳過：在結果寫「僅單一模型複查」後繼續。

**非互動情境**（`claude -p`、排程、workflow-bench、`/loop`）：一律跳過跨模型，並寫明「跨模型已跳過：非互動情境」。**沒有使用者明確授權，絕不呼叫外部 CLI。**

### 4. 分類

reviewer 的輸出是資料，不是判決。**對照產物原文**，每個發現依序套用，第一個符合的就是它的類別：

1. **契約沒寫清楚**：reviewer 會這樣講是因為契約缺東西。先補契約，下一輪再分類
2. **成立且要修**：改產物，再跑一輪
3. **成立但接受**：修的代價高於風險。寫明取捨，讓使用者看到
4. **雜訊**：在 reviewer 沒有的脈絡下其實是對的。記下來，並想想：契約補上那段脈絡，是不是就不會誤報

reviewer 沒有你的脈絡，可能是錯的；不要因為它是「新的眼睛」就照單全收。

### 5. 停止

符合任一條就停：

- 新一輪只剩瑣碎或已經考慮過的發現
- 已經跑了 3 輪（交給使用者，不要自己跑第 4 輪）
- 使用者說「就這樣」

3 輪後還有實質問題，代表這個決定還不成熟，交給使用者決定。覺得 3 輪不夠，是產物太大，回第 2 步拆小，不是放寬上限。

## 結果怎麼寫

```
doubt-check：<主張一句話>
- 複查：單一模型 ×N 輪；跨模型：<Codex 1 輪／使用者跳過／非互動情境跳過>
- 修了：<成立且要修的，一行一個>
- 接受的取捨：<…>
- 雜訊：<…>（契約已補／不需補）
- 結論：<定案／交給使用者>
```

寫進任務文件的「實作注意事項」，讓 stack-review 和之後的人看得到。

## 常見藉口

| 藉口 | 為什麼不成立 |
|------|-------------|
| 「我很有把握，跳過複查」 | 最有把握的時候最容易藏盲點。但只限上面的高風險決定，其他照常做 |
| 「開 subagent 很貴」 | 錯的寫法上線後再除錯更貴；複查最多 3 輪，有上限 |
| 「等最後 stack-review 再一起看」 | stack-review 看到時方向已經定了，改的代價高很多 |
| 「把我的推理一起給 reviewer 比較快」 | 給了結論就只會拿回背書。只給產物和契約 |
| 「reviewer 不同意，所以我錯了」 | 它缺你的脈絡；對照原文分類後再決定 |
| 「使用者上次同意用 Codex，這次也直接跑」 | 每次呼叫外部 CLI 都要重新確認指令與授權 |
| 「這次不推薦跨模型，就不用問了」 | 要不要花這個錢是使用者決定；可以說不推薦，但一定要問 |

## 警訊

- 對改名、改樣式這類小事開 reviewer
- 把 reviewer 的話當結論，沒有回頭看產物原文
- 超過 3 輪還沒交給使用者
- 提示詞寫成「這樣好嗎？」而不是「找出問題」
- 產物沒變又開一輪（結果會一樣，只是在拖）
- **兩輪以上 reviewer 都有實質發現，卻沒有任何一個被歸為「要修」**：你在背書，不是在複查。停下來交給使用者
- 互動情境默默略過跨模型的詢問
- 給 reviewer 的輸入少了契約，或多了主張

## 退場條件（2026-11-11 使用者決定）

這個 skill 是試用中的機制。從 0.2.0（由任務文件標記觸發、寫程式之前跑）起算，**接下來 3 張標了「需 doubt-check」的卡**，每張結束時記錄：有沒有照標記觸發、有沒有找到「成立且要修」的問題。

- 3 張都沒找到要修的問題，或標記規則實際上沒有發揮作用（標了卻沒跑、該標的沒標）→ **移除本 skill**，把高風險決定的檢查點併進 stack-review
- 至少 1 張找到要修的問題 → 保留，下一次檢討時再看

## 與其他工具的分工

| 工具 | 什麼時候 | 範圍 |
|------|---------|------|
| `doubt-check` | ④ 開發中途，碰到高風險決定 | 單一決定 |
| `tdd` | 有可測的行為時 | 一個會失敗的測試本身就是一次推翻的嘗試；行為類的主張有紅燈測試就算複查過 |
| `stack-review` | ⑤ 做完之後 | 整個 diff（規範＋對照任務文件） |
| `ai-pair` | 一開始就知道整個任務會動到多個高風險區塊 | 整個任務，多模型實作＋審查 |
| `diagnosing-bugs` | reviewer 指出的是真實失敗 | 定位與修正 |

## 檢查

- [ ] 每個高風險決定都先寫成主張
- [ ] reviewer 拿到的是產物＋契約，沒有主張和推理
- [ ] 提示詞是「找問題」，不是「好不好」
- [ ] 每個發現都對照原文、照順序分類
- [ ] 符合停止條件
- [ ] 互動情境有問過跨模型，回答寫進結果；非互動情境有寫明跳過
- [ ] 外部 CLI 每次都先確認存在、確認指令、取得授權，且用唯讀模式
