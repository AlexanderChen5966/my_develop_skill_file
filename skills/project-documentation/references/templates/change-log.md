# 變更歷程文件範本（通用）

適用於所有技術棧。此文件的主要消費者是**下游 repo 的開發者與 `/requirements`**——
他們需要低成本判斷「上游改了什麼、我要不要跟」，逐一 diff 原始碼成本過高。

---

## 標準結構

```markdown
---
title: [專案名稱] 變更歷程
type: change-log
created: YYYY-MM-DD
updated: YYYY-MM-DD
source-commit: <本次更新時的 HEAD>
status: in-progress
related-modules: [all]
---

# [專案名稱] 變更歷程

> 依時間**倒序**排列（最新在最上）。
> `⚠️` 標記表示**行為變更**（改動既有行為，非單純新增），下游必須確認影響。
```

## 撰寫規則

### 🔴 三者缺一不可

| 元素 | 為什麼 |
|------|-------|
| **Commit hash** | 下游要能 `git log <hash>` 精準定位，而非用日期猜 |
| **`⚠️` 行為變更標記** | 「新增」下游可以不跟，「行為變更」不跟就會壞。兩者混在一起等於沒分類 |
| **影響章節編號** | 下游只需要其中一小段，沒有章節就得整份重讀 |

### 「行為變更」的判斷

以下**都算**行為變更，必須標 `⚠️`：

- 既有端點的請求／回應**欄位增刪或改名**
- 欄位**語意改變**（型別不變但含義不同——最難察覺，一定要標）
- HTTP 狀態碼、錯誤格式改變
- 既有端點的**權限要求改變**
- enum **移除或改名**既有值
- 預設值、排序、分頁行為改變

單純**新增**端點／欄位／enum 值則不標 `⚠️`，但 enum 新增值需在「對下游的影響」點出
（下游若採非容錯解析，新增值同樣會造成故障）。

### ❌ 不要做的事

- ❌ 不要把 `git log` 原文照貼——需判斷「這筆是否影響對外契約」，內部重構不必列
- ❌ 不要省略 commit hash（僅寫日期無法定位）
- ❌ 不要在此文件解釋實作細節——這裡只回答「改了什麼、影響誰」
- ❌ 不要合併多次變更為一條而只留最新 hash——下游可能停在中間某個版本
