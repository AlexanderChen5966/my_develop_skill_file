# 畫面 Review（唯讀）

只看、只報告。**不編輯任何檔案**，包括 `DESIGN.md`。程式碼對不對由 `stack-review` 負責，不在這裡判斷。

## 流程

1. **確定目標**：使用者給的截圖、網址、或本機頁面。三者都沒有就問，不要自己挑一頁
2. **找規格**：往上找該專案的 `DESIGN.md`（從目標所在資料夾往上）。找不到就在報告開頭寫「沒有 DESIGN.md，以下只能評一般原則，不能評是否符合專案」，並建議叫 `design-md-init`
3. **取得畫面**：有瀏覽器工具就實際開頁、截圖；要看不同狀態（空、載入、錯誤、長文字、手機寬度）就逐一操作。**只有靜態截圖時**，沒拍到的狀態一律列在「沒法判斷」
4. **三軸分開看，不混著排**：
   - **規格**：顏色、字型、間距、圓角、元件是否符合 `DESIGN.md`；引用 token 名稱與實際看到的值
   - **去 AI 味**：照 `anti-ai-look` 的清單
   - **使用**：資訊層級、可點擊區域、狀態是否齊全、對比與字級是否讀得清楚
5. **每個發現要有證據**：位置（截圖區域或元素）、看到什麼、為什麼是問題、建議怎麼改。沒有證據的不列
6. 可選：網頁畫面若環境有 `impeccable`，把它的 critique／detect 結果當佐證列在最後，不當成結論

## 輸出

```
畫面 Review：<目標>
規格來源：<DESIGN.md 路徑／沒有>
看過的狀態：<列出>　沒看到的：<列出>

🔴 要改（違反規格或影響使用）
🟡 建議（品味、一致性）
🟢 可以保留（刻意的選擇，附理由）

去 AI 味：<成立的條目編號>
沒法判斷：<條目與原因>
交接：要修的項目交給開發角色，附上上面的位置與建議
```

## 邊界

- 設計稿（Figma）與實作的逐像素比對不屬於這裡；那是 `flutter-ui-compare`（網頁重寫成 Flutter Web 對照時）的工作
- 不要因為「改起來很簡單」就順手改檔；本 skill 沒有寫入權限的假設
