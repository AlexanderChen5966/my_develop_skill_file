# 參考文件可信度判斷（requirements Step 2a 的細節）

SKILL.md 的 Step 2a 讀到上游／既有架構、API 文件時，照本檔逐項判斷後才可採用。

## 🔴 可信度判斷（必做，不可略過）

這些文件是**描述性文件**——描述「現況是什麼」，**會與程式碼漂移**。
逐項判斷後才能決定要不要相信：

| 情況 | 動作 |
|------|------|
| 該項標 `⚠️ 推導未驗證` | 🔴 **必須翻原始碼確認**，不可直接採用 |
| 文件 frontmatter 的 `source-commit` 與該 repo 目前 HEAD 差距大 | ⚠️ 相關章節視為可能過期，**翻原始碼確認** |
| 文件**沒有** `source-commit` 欄位 | ⚠️ 舊版產出、無法判斷版本 → **全部視為未驗證** |
| frontmatter `status: superseded` | ⛔ **直接跳過此檔**，找取代它的版本 |
| 文件**逐章節標了不同可信度**（如「§3／§5 已校正、§4 未校正」）| ✅ 已校正章節可採用；**未校正章節視同未驗證** |
| 文件內容與需求相關章節**根本不存在** | 翻原始碼 |
| 上述皆非（有 `source-commit`、版本相近、未標未驗證） | ✅ 可直接採用，**在任務文件註明來源文件與章節** |

檢查上游 repo 是否有新變更未反映在文件裡：

```bash
# 上游 repo 的變更歷程文件——判斷「後端最近改了什麼」的低成本來源
grep -n "⚠️" ../b2b-backend/UPDATE_RECORD.md | head -20
```

## ⚠️ JSON 範例與序列化格式一律不可憑文件採信

**除非該處明確標示已從序列化配置確認**，否則 JSON 鍵命名、包裝層數、分頁欄位名
**一律翻原始碼確認**。

> 🔴 曾發生：後端 API 文件的 JSON 範例鍵命名全用 camelCase（實際是 snake_case，396 : 1），
> 分頁包裝類五個欄名全錯，前端照文件寫成 DTO 後 runtime 解析失敗、整頁空白。
> **這類錯誤在文件裡看起來完全正常**——語氣肯定、格式工整，沒有理由懷疑。
> 所以規則不是「小心一點」，而是**這一類內容預設不採信**。
